# 饭卜卜推荐轮换、性能与生产数据通道设计

日期：2026-08-17

状态：已确认

主仓库：`/root/miniapp-trellis`

## 1. 目标

- 产品展示名称统一为“饭卜卜”，文案为“今天吃啥嘞 · Eat-What，卜一卜 → 补一补”。
- 连续“换一套”至少变化两项；候选充足时三项全部变化。
- 忌口、过敏、体质禁忌和明确避雷的店铺＋菜品始终是硬过滤条件。
- 消除外食推荐固定复读，减少推荐链路的数据库往返和前端冗余请求。
- 为暖请求建立可观测的性能预算，不把冷启动和业务慢查询混为一谈。
- 保留 FastAPI + CloudBase 云托管 + `callContainer`，最终停止生产运行时使用 MySQL 公网直连。

## 2. 当前根因

### 2.1 外食固定复读

`external_dining.py` 对固定候选按相同分值稳定排序，既不读取最近展示记录，也不接收客户端排除项。同一输入必然返回相同三项。

### 2.2 自己做缺少双重轮换保障

后端已有推荐事件和当天曝光排除，但前端没有把最近结果作为软排除项回传。线上若事件写入、读取或用户身份链路异常，界面没有第二层防复读保障，也没有足够的分段日志说明失败发生在哪一段。

### 2.3 暖请求数据库往返过多

一次自己做推荐包含用户认证查询、重复档案查询、历史与事件查询、食物全表查询与重复计数、菜谱查询、日报 upsert、事件写入和多次 refresh；前端成功后又请求一次当天日志。公网 MySQL 将每次往返的网络延迟放大，约 1500ms 属于链路设计结果，而不是算法计算量。

## 3. 产品与交互规则

### 3.1 品牌边界

只修改用户可见名称、导航标题、登录页、首页 hero、应用描述和 FastAPI 文档标题。保留 AppID、CloudRun 服务名、API 路径、包名和 `eat_what_*` 存储键，避免品牌改名破坏登录态或线上配置。

### 3.2 换一套语义

- 客户端保存最近两批自己做 food ID 和外食 suggestion key。
- 请求携带软排除集合；后端与数据库中的曝光/选择历史合并。
- 相邻两批交集最多为 1，即至少两项变化。
- 每个餐盘角色候选充足时，主菜、蔬菜、主食全部更换。
- 候选不足时逐级放宽“近期展示”限制，但绝不放宽安全过滤。
- 候选完成一轮后允许最多一项重复，并通过响应状态提示“候选已轮换一轮”。
- 切换自己做/外食时清除另一模式的当前展示，避免旧结果伪装成新结果。

### 3.3 外食推荐

- 保持“只推荐吃什么，再由用户搜附近店”的产品边界。
- 规则分继续参考心情、活动量、个人/家庭、季节和私人记录。
- 喜欢记录每批最多召回一项；精确的避雷店铺＋菜品始终排除。
- 当前 8 个规则候选支持两批完全不同的三项，第三批至少变化两项。
- 本阶段不接商家、价格、下单或 Agent API。

## 4. 第一阶段架构

```text
Today 页面
  ├─ 本地最近两批排除项
  ├─ 已缓存天气快照
  └─ callContainer
        ↓
FastAPI 推荐接口
  ├─ 身份/档案（单次读取）
  ├─ 历史与事件
  ├─ 进程内只读食物/菜谱目录缓存
  ├─ 硬过滤 → 规则评分 → 强制轮换
  ├─ 单事务写推荐事件和今日日志
  └─ Server-Timing + request_id 结构化日志
```

### 4.1 性能改造

- 删除档案重复查询。
- `food_service.get_all()` 不再为 total 加载一次全表后又查询第二次；推荐热路径直接读取缓存目录。
- 食物与菜谱是部署期种子数据，在每个容器实例内建立有界只读缓存；重新部署自然失效。
- 推荐响应已经包含最新餐盘，前端不再紧接着调用 `GET /daily/today`。
- 页面已有且未过期的天气快照可随推荐请求传入；天气只作 ±3 分软修正。无有效快照时后端按现有超时与中性回退处理。
- 去掉仅为获得已知字段而执行的多余 ORM refresh。
- 用单调时钟记录 `auth/profile/history/catalog/weather/rank/write/total`，日志不记录密钥、经纬度和完整健康档案。

### 4.2 性能目标

- 暖实例自己做：P50 ≤ 700ms，P95 ≤ 1200ms。
- 暖实例外食：P50 ≤ 400ms，P95 ≤ 800ms。
- 冷启动单独标记，不通过提高最小实例数掩盖暖请求慢查询。
- 本地纯推荐计算 500 候选维持在 500ms 内。

## 5. 第二阶段：CloudBase MySQL HTTPS Repository

最终运行链路：

```text
微信小程序 → callContainer → FastAPI → CloudBase MySQL HTTPS REST API → MySQL
```

- 在 service 与存储之间新增 Repository 协议，先保持 SQLAlchemy 实现，再增加 CloudBase REST 实现。
- CloudBase API Key 仅存于云托管服务端环境变量 `CLOUDBASE_DB_API_KEY`，不得出现在小程序、Git、镜像或日志中。
- FastAPI 继续校验自有 JWT，并在每个用户数据仓储方法中强制加入 `user_id`；前端不得传入或覆盖所有者身份。
- HTTP REST 的多请求不能冒充数据库事务。推荐事件使用唯一 `request_id` 幂等写入并作为权威记录，日报投影允许安全重试和修复。
- GET 可对网络错误进行一次短重试；写请求仅在带幂等键时重试。
- Alembic 迁移继续保留为 schema 真相源；正式变更通过 CloudBase SQL 编辑器或已验证的管理工具执行。生产运行期间关闭 3306 外网直连。
- 在拿到真实 API Key 与官方 OpenAPI 后先做只读 shadow 验证，再切换写入；没有云端证据时不声称迁移完成。

## 6. 错误与降级

- 天气失败：使用中性天气，推荐继续。
- 数据库历史读取失败：不伪造新鲜度；返回明确错误或客户端上次缓存，并标记只读。
- 推荐事件写入失败：不得把结果声明为“新一套”；客户端保留旧结果并显示请求编号。
- 排除后角色候选不足：只放宽近期重复限制，不放宽任何安全限制。
- HTTP Repository 未配置或认证失败：生产启动/健康检查失败关闭，禁止静默退回公网 DSN。

## 7. 测试与验收

- 后端：连续四批、候选充足时 12 个 food ID 唯一；一般情况下相邻两批交集不超过 1。
- 后端：外食连续三批满足相邻两批至少变化两项，避雷精确对始终不返回。
- 后端：忌口与体质禁忌不会因排除集合过大而回补。
- 前端：模式切换清理旧结果；请求携带正确排除项；推荐成功不再额外获取今日日志。
- 性能：结构化日志和 `Server-Timing` 包含各阶段耗时，且无敏感信息。
- 工程：Ruff、mypy、pytest、ESLint、TypeScript、Vitest、H5 与 mp-weixin 构建全部通过。
- 云端：微信开发者工具模拟器和真机完成登录、连续轮换、收藏、备注、历史及错误回退验证。
