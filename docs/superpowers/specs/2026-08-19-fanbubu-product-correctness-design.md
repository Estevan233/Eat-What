# 饭卜卜推荐与首屏体验修复设计

## 目标

本轮只处理上线前的四条用户可见主链路：个人外食必须稳定给出三个不同方向；家庭自己做必须按人数改变菜数和结构；健康档案输入不得裁切；首次体质测试不得把“尚无记录”展示成错误。数据库 HTTPS Repository 迁移暂缓到这些功能稳定后，现有 FastAPI + CloudBase 云托管 + MySQL 链路保持不变。

## 已确认根因

1. 个人外食候选默认共用 individual_meal，服务端又按 meal_format 去重，最终只保留一项。
2. 做饭推荐从 Schema、构建器到确认接口均假设恰好一个 main、一个 vegetable 和一个 staple；party_size 没有参与菜单结构。
3. 规则排序按固定分数和 food id 决胜，七日曝光只记录最近一次并做软扣分，不能稳定压住长期高分菜。
4. 微信小程序原生 input 的默认高度与纵向 padding 冲突，造成数值字形上下裁切。
5. 体质 GET 的正常 404 在页面接管前被统一请求层弹成 Toast。

## 个人外食合同

- 每次成功推荐返回三项；同批 key、meal_format 均不重复。
- 个人规则候选不少于十二项，覆盖米饭套餐、面食、粥品、蒸菜、砂锅、汤食和轻食等不同餐型。
- 客户端最近六个 key 优先排除；候选池轮完后才允许复用，并用 rotation_restarted 明示轮换重启。
- 忌口与体质禁忌始终是硬过滤；安全候选不足三项时返回真实数量，不能复制凑数。

## 家庭自己做合同

人数对应的默认角色模板：

- 1 人：main, vegetable, staple
- 2 人：main, vegetable, staple
- 3–4 人：main, main, vegetable, staple
- 5–6 人：main, main, vegetable, vegetable, staple
- 7–8 人：main, main, main, vegetable, vegetable, staple

构建器允许同一角色出现多次，但 food id 不能重复，并优先避免相同烹饪方式。家庭多槽位版本暂不提供按角色替换，因为仅靠 target_role 无法唯一定位第二道主菜；先保证整套刷新和确认正确，后续再用稳定 slot_id 恢复单槽替换。

确认家庭餐时，客户端必须提交本次推荐快照中的全部 food id，数量与快照一致，不得额外加入其他菜。个人三槽位的现有替换合同保持兼容。

轮换规则：客户端保存最近十二个做饭 food id，足以覆盖最大规格的最近两批；候选充足时新批次至少替换向上取整的 N×60% 项。服务端七日历史同时考虑距今天数和曝光次数，完整套餐不因固定分数每天回到同一组合。硬过滤永不为多样性让路。

前端标题由快照动态生成，例如“两主菜 · 一蔬菜 · 一主食”，列表 key 使用 food id，避免重复角色造成 Vue key 冲突。营养摘要继续以每人份估算为主，并在家庭模式补充全桌能量估算。

## 健康档案输入

身高与体重 input 使用明确高度、行高和零纵向 padding，保留左右 padding。现有身高 80–250 cm、体重 30–300 kg 校验不变；构建产物必须在微信小程序端通过。

## 体质空状态

统一请求层增加按 HTTP 状态静默 Toast 的窄接口。体质结果 GET 只静默 404，Promise 仍正常 reject；用户 Store 将明确的 404 转成 null 并清理旧缓存，网络错误与 5xx 继续抛出且不误删已有结果。页面用 null 进入正常 0/9 问卷态，九题、提交和重测流程全部保留。

## 数据库边界

本轮不迁移 Repository，不关闭公网 MySQL，也不引入 Server API Key。功能稳定后另开迁移任务，依次验证服务端密钥、用户隔离、过滤、Upsert、错误映射和事务语义；只有所有直连依赖清零并完成回退演练后，才关闭公网 MySQL。

## 验收

1. 个人外食连续请求两批，每批三项，六项不重复且每批餐型不同。
2. 2、4、6、8 人自己做分别返回 3、4、5、6 项，角色数量符合矩阵；确认整套成功。
3. 相邻家庭套餐在候选充足时至少替换向上取整的 N×60% 项。
4. 身高体重默认值、占位符和输入值在 mp-weixin 构建后无纵向裁切。
5. 新用户进入体质测试显示 0/9，无 constitution 不存在 Toast；真实网络错误仍可见。
6. 后端、前端测试、类型检查、mp-weixin 构建与 Docker 镜像构建全部通过。
