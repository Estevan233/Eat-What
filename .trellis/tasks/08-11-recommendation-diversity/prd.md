# 优化推荐多样性并预留 Agent 扩展

## Goal

降低天气对排序结果的支配程度，并实现“当天刷新换一批、近 7 天减少重复”的推荐体验；在不引入模型调用和额外费用的前提下，为后续 Agent 重排保留稳定边界。

## Requirements

### 推荐质量

- 忌口和体质禁忌继续作为硬过滤，任何软评分、Agent 或多样性逻辑都不得重新引入被过滤菜品。
- 天气维度最高 15 分，最强匹配与明显不匹配的差值不得超过 12 个原始分。
- 补充体质适配评分，并重新平衡节气、心情、营养、活动量与星座分值。
- 对规则分、可选重排调整和新鲜度惩罚求和后截断并归一化到 0～100，继续满足现有 `FoodWithReason.score` 契约。

### 新鲜度

- 当天已推荐菜品在候选足够时不重复出现；候选不足时允许按降权后的顺序回补。
- 最近 7 天选过的菜强降权，惩罚随时间衰减。
- 最近 7 天推荐过但未选择的菜轻降权，惩罚随时间衰减。
- 同一道菜同时命中“选过”和“推荐过”时只应用较强的选择惩罚，避免重复扣分。

### 多样性

- 多样性重排基于全部合格候选，不再先截断到 Top 6。
- 候选充足时，最终 3 道菜的 `category` 与 `cooking_method` 均互不相同。
- 候选不足时按“先放宽做法、再放宽品类”的顺序降级，始终尽力返回 3 道菜。

### 推荐事件

- 每次成功推荐写入独立推荐事件，不覆盖当天之前的曝光记录。
- 事件只保存推荐所需的最小上下文，不保存经纬度、完整用户档案或其他敏感信息。
- 当前 `DailyLog` 仍保存当天最新一批推荐与实际选择，现有 today/history 接口语义不变。

### Agent 扩展边界

- 当前版本不接入任何 LLM/Agent SDK，不增加模型密钥、网络依赖或调用费用。
- 推荐管线拆分为硬过滤、规则评分、可选候选重排调整、新鲜度与多样性重排、持久化五个阶段。
- 后续 Agent 只能对已通过硬过滤的数据库菜品 ID 重排和生成理由；输出必须校验且失败时回退规则结果。

### 兼容性

- `POST /api/v1/daily/recommend` 的请求和响应 JSON 结构保持兼容，前端无需同步修改。
- `GET /daily/today`、`GET /daily/history` 和 `POST /daily/choose` 行为保持兼容。
- 新表通过 MVP 现有 `SQLModel.metadata.create_all` 创建，不修改已有表结构。

## Acceptance Criteria

- [ ] 合格且当天未曝光菜品不少于 6 道时，连续两次推荐结果无重复。
- [ ] 合格且当天未曝光菜品不少于 12 道时，连续四批推荐共 12 道菜无重复。
- [ ] 存在至少 3 道可替代菜时，近 7 天选择过的菜不进入最终推荐。
- [ ] 候选的品类和做法足够丰富时，单批 3 道菜的品类和做法均不重复。
- [ ] 候选不足时仍返回最多 3 道不同菜品，不抛出多样性相关异常。
- [ ] 所有天气分支符合新分值上限，并保留合理的冷、热、雨、雪、干燥偏好。
- [ ] 应用重排调整和新鲜度惩罚后，对外 `score` 始终位于 0～100。
- [ ] 每次成功推荐新增一条 `RecommendationEvent`，同时 `DailyLog` 仍只保留当天最新一批推荐。
- [ ] 推荐事件不包含原始经纬度、生日、身高、体重或完整体质档案。
- [ ] 现有 API 响应结构保持不变，既有后端测试与新增回归测试全部通过。
- [ ] 200 道菜规模下，纯规则推荐服务耗时继续小于 500ms（不含天气 HTTP 请求）。
- [ ] 当前依赖中不新增 Agent/LLM SDK。

## Out of Scope

- 本任务不接入实际 Agent、不选择模型供应商、不设计付费策略。
- 本任务不实现菜谱详情、整道菜总热量或份量换算；这些另开功能任务，避免把推荐算法改造成一锅需求乱炖。
- 本任务不引入 Alembic；生产上线前仍需单独补齐正式迁移。
