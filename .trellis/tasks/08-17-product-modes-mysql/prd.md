# 完善用餐模式并完成 CloudBase MySQL 落地

## Goal

在保持现有“完整餐＋菜谱＋微信登录”链路兼容的前提下，使生产后端真正可迁移至 CloudBase MySQL，并让用户在首页选择“自己做”或“点外卖/到店吃”、个人或家庭人数；外食结果允许记录私有的店铺＋菜品备注与精确避雷。

## Requirements

- 唯一开发仓库为 `/root/miniapp-trellis`；Windows UNC 只读取同一仓库的构建产物。
- 生产配置不得静默使用 SQLite；所有 Alembic revision 必须能为 MySQL 8 编译并在真实 MySQL 烟测。
- 小程序默认保持 `自己做 + 个人 + 1 人`，旧客户端请求不受影响。
- 家庭 MVP 只记录本次人数 2-8，并以当前账户忌口作为安全边界；成员独立档案留待后续 Household 任务，界面不得伪称已综合全家体质。
- 外食 MVP 不接第三方下单或商户 API，只给出菜品/品类、搜索关键词、点单提示、估算能量区间与推荐解释。
- 店铺＋菜品记忆为用户私有，`liked | neutral | avoided` 互斥；`avoided` 只屏蔽完全相同的店铺＋菜品组合。
- 硬性忌口永远先于所有软评分；节气食养仅作一般饮食参考，不作诊断或疗效承诺。
- 推荐解释权重目标：营养 22%、节气食养 18%、个人/家庭目标 20%、偏好与历史 15%、可执行性 15%、多样性 10%；天气仅为节气食养内 ±3 分修正。
- 当前 CloudBase 主环境仍为 `cloud1-d8gz4jm8vb964a1c9`，预发环境为 `tx-clouddev-d3g8w4jpif0222220`，二者均手动续费。

## Acceptance Criteria

- [ ] MySQL 方言可从空库编译全部迁移，`foods.description` 不再生成无长度 VARCHAR。
- [ ] `ENVIRONMENT=prod` 配 SQLite、DEBUG=true、code2session=true 或非 HS256 时启动校验失败。
- [ ] 迁移/播种为显式发布步骤，应用容器启动不并发执行 DDL。
- [ ] 旧请求仍返回现有完整餐；新请求可保存 dining mode、audience 和 party size。
- [ ] 外食接口在无定位、无历史时仍返回可理解的确定性建议。
- [ ] 用户可增改删精确店铺＋菜品记忆，跨用户不可见。
- [ ] 精确避雷组合不再进入外食结果，但同店其他菜和其他店同名菜仍可出现。
- [ ] 家庭人数只影响本次建议与份量语义，不伪造家庭成员档案。
- [ ] 小程序模式选择可持久化，切换模式后旧推荐缓存失效。
- [ ] 后端全量质量检查、前端测试/类型/双端构建全部通过。
- [ ] 文档包含 CloudBase MySQL VPC、内网连接、最小权限账号和发布烟测步骤。

## Out of Scope

- 美团、饿了么、大众点评或地图商户实时 API 与下单跳转。
- Household/HouseholdMember 长期家庭档案、家庭邀请与成员授权。
- Agent 在线推荐、自动生成营养值或医疗建议。
- 自动操作腾讯云控制台、创建数据库或写入用户云资源。
