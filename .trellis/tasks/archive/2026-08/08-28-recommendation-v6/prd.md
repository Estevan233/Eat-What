# rules_v6 多样性与 30 天偏好画像

## Goal

在不改变忌口、体质禁忌、菜谱完整性和完整餐角色约束的前提下，把现有 `rules_v5` 升级为可解释、可复现的 `rules_v6`：85 分基础相关性负责“适不适合”，15 分重排负责“这一批是否新鲜且不单调”，并用近 30 天收藏与实际选择形成轻量偏好画像。

## Product principles

- 安全和数据完整性先于任何分数。硬过滤后的菜才能进入评分、探索和多样性重排。
- 基础相关性与重排职责分离。探索不能把明显更差的菜包装成“惊喜”，多样性也不能拿忌口当橡皮筋。
- 可复现不等于永远按 `food.id` 排序。同一用户、日期、请求种子必须稳定；不同请求可以在质量相近的候选中变化。
- 没被展示过不是“不喜欢”，展示后没选也不是明确差评。只有显式负反馈才允许产生负向偏好证据。
- 节气、性味和体质只作一般饮食参考，不得生成诊断、治疗或疗效承诺。

## Requirements

### R1. 候选安全边界

- 当候选进入排序管线时，系统必须先执行现有 `recipe_ready`、用户明确排除食材、忌口标签和体质禁忌硬过滤。
- 当软评分、14 天新鲜度、30 天探索、多样性或未来 Agent 重排执行时，系统不得重新引入被硬过滤的 `food_id`。
- 当某个完整餐角色的安全候选不足时，系统必须返回现有可解释错误，不得复制菜品或放宽安全约束凑数。

### R2. 85 分基础评分

系统必须使用下列独立分项，基础分上限严格为 85：

| 分项 | 上限 |
|---|---:|
| 营养互补 | 12 |
| 体质适配 | 14 |
| 节气周期 | 16 |
| 天气适配 | 4 |
| 近 30 天偏好 | 15 |
| 场景可执行性 | 14 |
| 心情 | 5 |
| 活动量 | 3 |
| 星座彩蛋 | 2 |
| **合计** | **85** |

- 当旧客户端不传 `meal_intent` 时，场景可执行性仍必须由做法和耗时得到稳定分数。
- 当存在 `meal_intent` 时，已有食材、时间预算和目标只能在 14 分场景分项内调整，不得继续以额外分数叠加到 85 分之外。
- 天气失败或用户未授权定位时，系统必须使用中性天气分，推荐继续执行。

### R3. 节气周期分档

- 系统必须按上一节气日期、下一节气日期和当前日期计算当前节气周期，不再只在节气当天命中满分。
- 当前周期必须分为前、中、后三档；当前节气标签分别获得 16、12、8 分，下一节气标签分别获得 0、4、8 分。
- 节气当天必须归入新周期前段；同一道菜同时标注当前和下一节气时取较高档，不累加。
- `TodayContext` 既有对外语义必须保持不变；周期计算应作为排序内部上下文，避免把“当前节气”字段悄悄改成另一种含义。

### R4. 15 分受约束重排

系统必须把最终 15 分限定为两个重排分项：多样性 7 分、探索 8 分。

- 多样性必须在组装当前餐单时按已选菜动态计算：新 `category` 贡献 3.5 分，新 `cooking_method` 贡献 3.5 分；候选不足时降低多样性分，不得过滤掉必需餐位。
- 探索必须以每个 `meal_role` 的“基础分加新鲜度惩罚”最高值为参照，只允许距最高值不超过 5 分的质量带候选进入探索池。
- 只有近 30 天从未曝光且位于质量带内的候选才能获得 8 分探索资格；近 30 天未曝光不得对全候选固定加 8 分。
- 当质量带内没有 30 天未曝光候选时，不得为了凑探索分扩大质量带。

### R5. 14 天新鲜度与当天强惩罚

- 系统必须读取包含当天在内的近 30 天推荐事件和选择日志，其中仅最近 14 天用于新鲜度惩罚。
- 当菜品当天已曝光时，新鲜度惩罚必须为 `-45`；安全候选不足时它仍可回补，但不得像 `rules_v5` 一样在候选充足时另走一套硬删除逻辑。
- 第 1～13 天的选择惩罚必须强于曝光惩罚并随时间单调衰减；第 14 天及更早不得再扣新鲜度分。
- 同一道菜同时命中当天曝光、近期选择、近期曝光和重复曝光时，只应用最强的一项，不得层层相加把分数炸穿地板。

### R6. 排序确定性

每次选择候选时必须按以下顺序决胜，任何前置项不同都不得提前比较后置项：

1. 最终分降序；
2. 距最近曝光天数降序，30 天内未曝光视为最远；
3. `user_id + 日期 + request seed + food_id` 生成的稳定哈希序；
4. `food.id` 升序，仅作最终兜底。

同一用户、日期和请求种子重复计算必须得到完全相同的餐单；不同用户或不同请求种子只能在前两项相同的候选中改变顺序。

### R7. 近 30 天偏好画像

- 系统必须使用包含当天在内的近 30 天 `Favorite.created_at` 和 `DailyLog.chosen_food_ids_json`，不得继续沿用 7 天窗口或把全部历史无期限累加。
- `rules_v5` 已有 `category`、`cooking_method`、`ingredient` 画像必须复用；`rules_v6` 增加 `tags` 与 `nature`，并保留 ingredient 的低权重兼容信号。
- 收藏作为显式正反馈，权重必须高于选择；两者均按 0～6、7～13、14～20、21～29 天分档衰减。
- 隐式选择必须按该菜近 30 天曝光次数做保守衰减，避免系统反复曝光某类菜后再拿自己制造的数据证明“用户就爱这个”。
- 未曝光、曝光未选和客户端 `exclude_food_ids` 不得自动写成负偏好。
- 无有效画像时偏好分必须回到中性基准，不得因冷启动得到 0 分。

### R8. 显式负反馈扩展边界

- 排序领域层必须预留带日期和动作类型的显式负反馈输入，至少区分 `not_interested` 与 `hide`；当前推荐主链路默认传空集合。
- 显式负反馈只能降低软偏好或 exact-item 排序，不能取代忌口/体质硬过滤，也不能从“未选择”推断生成。
- 本任务不新增负反馈数据库表、HTTP 路由或前端按钮；未来接口必须校验推荐事件归属及 `food_id` 确实出现在该事件中后，才能把信号交给画像构建器。

### R9. 兼容性、可观测性与性能

- `POST /api/v1/daily/recommend` 的请求结构和顶层响应结构必须保持兼容；响应 `engine`、推荐事件 `engine/scorer_version` 必须写 `rules_v6`。
- `weight_profile` 必须保留现有聚合字段并以新增字段公开节气、天气、体质、心情、活动、星座和探索明细，避免旧客户端因删键失效。
- 推荐事件继续作为曝光事实来源，不新增经纬度、生日、体重、完整体质问卷或候选全集等敏感字段。
- 200 道合格候选下，排除天气 HTTP 后的完整规则推荐必须小于 500 ms；推荐热路径数据库查询不得超过现有 5 次基线。
- 本任务不得新增 LLM/Agent SDK、模型调用、在线训练或新的数据库迁移。

## Acceptance criteria

- [ ] 自动化测试证明基础分九个分项上限精确为 `12/14/16/4/15/14/5/3/2`，合计 85；多样性与探索上限精确为 `7/8`，最终对外分数始终在 0～100。
- [ ] 自动化测试证明 meal intent 不再作为 85 分之外的额外 `±6` 分存在。
- [ ] 固定节气周期的前、中、后三个边界日分别命中 `16/12/8`，下一节气命中 `0/4/8`，节气当天正确切换新周期。
- [ ] 当天曝光惩罚精确为 `-45`；第 1～13 天惩罚单调衰减；第 14 天为 0；选择与曝光同时命中时只取更强值。
- [ ] 质量带外的 30 天未曝光候选探索分为 0；质量带内的未曝光候选可得 8；扩大请求种子不改变质量带成员。
- [ ] 构造同最终分候选时，先选更久未曝光者；距离相同后才由稳定种子决胜；前三项仍相同后才按 id。
- [ ] 同一 `user_id/date/request_id` 重放得到相同推荐，不同用户或不同 request id 在并列候选上至少存在一个可复现的顺序差异。
- [ ] 候选特征足够时，最终餐单的 category 与 cooking_method 尽量不同；候选不足时仍满足主菜、蔬菜、主食角色数量且不重复 `food_id`。
- [ ] 30 天画像覆盖 tag、category、nature、cooking_method 和兼容 ingredient；第 30 天之外的收藏与选择不计入。
- [ ] 同样的隐式选择证据下，曝光次数更多的菜贡献不高于曝光次数更少的菜；曝光未选不产生负分；显式负反馈测试只通过注入接口生效。
- [ ] 既有忌口、体质禁忌、幂等请求、天气降级、完整餐与推荐事件测试继续通过。
- [ ] `ruff check app/ tests/`、`mypy app/` 和完整 `pytest tests/ -q` 全绿；目标服务覆盖率不低于 80%。
- [ ] 200 候选性能测试小于 500 ms，热路径查询计数不超过 5。

## Out of scope

- 负反馈表、负反馈 API、前端“不感兴趣/隐藏”交互及历史数据回填。
- 基于 propensity 的因果去偏、在线 bandit、A/B 实验平台和机器学习训练；现有事件缺少展示位置与选择概率，不能一本正经地假装已经无偏。
- 500+ 候选库扩充、`nature=unknown/cold/hot` 数据补齐和节气标签补标；这些由相邻候选库任务负责。
- 外食方向排序、微信身份合并及游客数据迁移。
