# 总体设计

## 架构边界

```text
微信可信身份 / 游客 JWT
        ↓
身份合并服务 ──→ 统一 user_id
        ↓
收藏、选择、曝光、外食反馈
        ↓
30 天偏好快照
        ↓
硬过滤 → 85 分基础相关性 → 15 分多样性/探索重排
        ↓
结构化家庭候选与外食方向
        ↓
小程序展示 / 后续受约束 Agent
```

## 数据责任

- `users` 是身份归属源；微信 OpenID 仅来自 CloudBase 可信链路。
- `recommendation_events` 是曝光源；`daily_logs` 是每日推荐与选择投影。
- `favorites`、`dining_memories` 和显式反馈用于偏好学习；曝光本身不是正向偏好。
- 家庭 Food/Recipe 与外食方向采用共享分类词表，但保留不同的数据生命周期。
- AI 只消费候选 DTO，不直接读写原始健康档案或自行持久化偏好。

## rules_v6 分数

- 基础相关性 85：营养 12、体质 14、节气 16、天气 4、偏好 15、场景可执行 14、心情 5、活动 3、星座 2。
- 重排 15：候选间多样性最多 7、质量带探索最多 8。
- 硬过滤不计分；同日与近 14 天重复使用负分/排除，不伪装成基础相关性。
- 对外 score 是排序解释分，不是喜欢概率或医学评分。

## 兼容与安全

- SQLAlchemy 路径使用数据库事务；CloudBase REST 路径使用可重入步骤与迁移状态，所有步骤必须幂等。
- 正式资料优先；游客资料只填补缺失字段。
- 合并后游客身份标记为迁移/停用，旧 Token 在每次鉴权查用户时被拒绝。
- 任何数据模型和 API 变化都提供 Alembic 迁移、REST Repository 测试和回滚说明。

## 发布策略

1. 身份合并可独立发布，默认不影响从未使用游客模式的正式用户。
2. rules_v6 通过 engine version 切换并保留 rules_v5 回退能力。
3. 候选扩充先通过脚本校验和离线分布报告，再进入可推荐状态。
4. 部署前必须重新跑 CloudBase 代码审查、后端全测、前端测试/类型检查/构建和真机登录回归。
