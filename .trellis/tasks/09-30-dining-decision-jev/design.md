# 技术设计草案（待评审）

## 推荐主链
现有结构化偏好/可选自然语言意图 → 后端硬过滤 → 分品类召回 → 规则基础分 → 可选 Jev 语义分 → 程序多样化选集 → 曝光持久化。
地图仅作为独立可选数据来源；附近参考失败不影响上述主链。私人店＋菜记忆沿用既有服务。

## 先查重复再引入模型
1. 记录候选来源 catalog/legacy/memory、回退原因、过滤前后数量、质量带内数量；不记录密钥或敏感原文。
2. 核验前端换一批生成新 request_id、网络重试复用原 ID；核验 CloudBase 曝光写入及历史查询。
3. 跨轮按稳定 ID 排除已曝光；按餐型、主料和烹法定义相似度，识别鸡丝面/鸡肉面等弱变体。
4. 不只截取原算法最高分 Top-K：按类别、用户喜好、低曝光候选分层召回，避免模型永远只能重排同几道菜。
5. 探索奖励有上限，显式负反馈优先于推断喜好。低曝光不等于适合用户；未点击不等于讨厌。
6. 当候选不足时返回说明或较少选项，不放宽忌口、虚构候选或偷偷扩大地理范围。

## Jev 适配器实验
- 服务端调用 POST /v1/systemone，凭据仅服务端持有；不把其当作现有 CloudBase generateText 的可直接替换模型。
- 固定实验版本 jev-1.13.0，记录返回版本、rubric 版本、耗时、输入 token、失败类别；价格/版本接入时再核验。
- 首轮最多召回约 20–30 个真实候选（实验参数，需按 token 与延迟调整），不把 500+ 菜谱和全量历史塞入 state。
- 给每个候选独立问题：是否匹配当次口味/餐型诉求？是否匹配已表达偏好？以带锚点的 0–4 Score 评估，包含“证据不足”。
- 每个问题明确引用候选 ID 和字段；文本只是数据，不执行其中指令；返回 ID、问题集合及数值范围由程序校验。
- 排名实验形式：规则基础分 + 有界语义分 - 历史/已选相似度惩罚；不预设未经标注验证的最终权重。
- 可采用逐项选取的多样化重排（类似 MMR）；距离、预算数值、曝光天数、份量运算全部留在代码。
- Confidence 仅辅助校验，不等于用户喜欢概率；不复制厂商或其他领域阈值。越界/低可信/超时/429 均用规则结果。
- 单次推荐最多一次模型批量评估；设置总耗时上限及限流，避免 SDK 自动重试放大等待。具体阈值按真实云端测试定。
- Jev 不生成解释。第一版用事实模板给短理由；现有生成模型仅保留意图抽取，不叠加多次模型调用制造慢链路。

## 腾讯地图辅助
- 不新增常驻地图页或强制权限；只在用户主动打开附近参考时获取必要位置。
- 启用前核验小程序主体/类目、接口权限、隐私声明、腾讯商业许可与账号额度；未满足则功能不开放。
- 保留 source、检索时间和字段缺失语义；地图 POI、私人记忆、通用餐食方向不混为店内实售菜单。
- 不将精确位置传给 Jev；不默认长期存储位置、不将地图数据批量镜像入自建库；缓存遵守许可。

## 兼容、隐私与回滚
家庭 rules_v6 与外食规则分别评估，先以外食为实验重点，不把两个评分系统直接混用。
保留现有 MealIntent 契约、登录链路与 HTTP Repository；现有前端 AI 入口与地图入口均可关闭。
Jev 由外部服务处理数据；“不用于训练”不等于零留存或符合跨境要求。先用合成数据；生产数据另行审查授权、传输及留存。
阶段开关：规则优化、Jev、附近参考独立。模型关闭后不读模型缓存、不影响基础推荐；上线只允许小流量灰度且可立即回退。
